# 《Function-Agent》项目演讲大纲

> 主题：纯前端 AI 数学助手 —— 29 个可视化工具 + Function Calling，让抽象数学看得见摸得着
> 时长：建议 12–15 分钟
> 受众：技术评审 / 项目答辩 / 学习分享

## 一、开场（1–2 分钟）

**自我介绍 + 一句话定位**

> "大家好，今天我带来的是一个叫 **Function-Agent** 的项目。它是一个**纯前端**的高等数学 AI 助手，核心卖点只有一句话：让 AI 答数学题的时候，**直接画出图来给你看**。"

**抛出痛点**

- 你有没有过这种经历：问 AI"极限是啥"，它给你吐一段 LaTeX 公式 —— 你看了五分钟还是没懂
- 或者想看泰勒级数怎么逼近原函数，纯文字描述脑补不出来
- 现有的 AI 数学工具要么必须联网，要么强制绑定单一模型，要么界面学术到劝退

**亮出解法**

> "Function-Agent 的解法是：**用 LLM Function Calling 自动调度 29 个前端可视化组件**，把抽象概念变成可拖拽、可缩放、可交互动画。"

**为什么这次分享值得听**

- 0 后端、0 构建、0 CDN —— 双击 HTML 就能跑
- 用户自带 API Key，零运营成本
- 4 段 Prompt 编辑、密文加密导出、数学符号键盘等 5 个新增模块

## 二、项目概览（1–2 分钟）

### 1. 是什么
一个 Web 端 AI 聊天应用，但**不只聊天** —— AI 会主动调用绘图组件、动画组件、解题卡片组件来回答数学问题。

### 2. 覆盖范围

| 数学分支 | 工具数 | 代表功能 |
|---------|--------|---------|
| 微积分 | 12 | 函数图像、极限动画、泰勒级数、3D 曲面 |
| 线性代数 | 2 | 矩阵变换、特征向量 |
| 概率统计 | 2 | 7 种概率分布、中心极限定理动画 |
| 级数与数列 | 2 | 傅里叶级数、数列蛛网图 |
| UI 辅助 | 6 | LaTeX 渲染、解题卡片、参数滑块、对比表、交互测验 |
| 学习辅助 | 5 | 公式手册、抽认卡、易错点分析、交互证明、概念图 |

### 3. 技术栈一句话总结
- 运行时：**原生 ES Modules**，没有 Webpack/Vite 那一坨
- 渲染：**Plotly 2D/3D + Canvas 2D + KaTeX**
- 状态管理：**自研发布-订阅 Store**，30 行代码搞定
- 持久化：**localStorage**，会话、设置、收藏、学习统计全在浏览器

## 三、核心亮点（这是重点，5–7 分钟）

### 亮点 1：四段式解耦的工具链架构 ⭐⭐⭐

**问题**：传统方式每加一个工具就得改一堆核心代码，开发者累死。

**我们的做法**：`Schema → Definition → Registry → Renderer` 四步走

```
schemas.js          → 写参数定义（给 LLM 看）
definitions/*.js    → 写执行逻辑（怎么算）
registry.js         → 注册到一张 Map 里
components/math/*   → 写前端怎么画
```

**加一个新工具只要 7 步**（README 里写得很清楚）：

1. 写 Schema
2. 写 Definition
3. 写 Renderer
4. 注册 Definition
5. 注册 Renderer
6. 更新映射表
7. 更新 Prompt

**完全不用动** `executor.js`、`ai-client.js`、`stream-parser.js`

> 现场可以演示：现在我们已经有 29 个工具，开发过程零侵入核心代码。

### 亮点 2：Agent Loop 编排 —— 让 AI 学会"多轮工具调用" ⭐⭐⭐

**讲个故事**：用户问"画出 sin(x) 及其泰勒展开到第 5 项"

**AI 的思考路径**（不是我们写死的，是 LLM 自己决定的）：
1. 先调 `plot_function` 画 sin(x) 原函数
2. 再调 `animate_taylor_series` 演示泰勒级数逐项逼近过程
3. 可能还会调 `render_latex` 给个公式对比
4. 最后用自然语言总结

**技术实现**（在 `chat-area.js` 的 `runAI` 函数里）：

```
while (true) {
   1. 构建 messages（过滤占位/错误/思维链）
   2. SSE 请求 LLM
   3. 如果返回 toolCalls → 逐个执行 → 把结果喂回 messages
   4. 如果没 toolCalls → 结束 + 自动生成标题
}
```

**并发安全**（这是踩过的坑）：
- `MAX_TOOL_DEPTH=25` 防止无限套娃
- `_runAIGeneration` 代际守卫，防止旧请求覆盖新状态
- `_activeStreams` 双重保险计数
- `isStreaming` 复位权**独占**在 `runAI` 的 `finally` 块里 —— 这是我们调试时血的教训

> 现场可以打开 console 演示一次：发个问题，看 messages 数组怎么被 LLM 一轮轮填满工具调用和工具结果。

### 亮点 3：29 个可视化组件，每个都"能动手" ⭐⭐

**不是静态截图，是真交互**：

| 工具 | 交互方式 |
|------|---------|
| `plot_function` | Plotly 缩放/平移/悬停看坐标 |
| `animate_limit` | 滑块控制 x 趋近过程 |
| `plot_integral_area` | 拖拽区间端点改积分上下限 |
| `control_parameter_slider` | 滑块联动函数图像（参数 a 变化看曲线变形）|
| `animate_solid_of_revolution` | 3D 拖拽旋转 |
| `interactive_quiz` | 5 种题型混合选择，AI 实时判分 |

**细节中的魔鬼**：
- 未聚焦时图表 `pointer-events: none` —— 滚轮**穿透**到页面，不卡顿
- 点击卡片进入聚焦态才响应交互
- 全屏模式用 `ResizeObserver` 监听 Canvas 重绘
- 暗色主题用**钢蓝色**（`#7e9cb0`）而非纯黑，护眼不刺眼

### 亮点 4：System Prompt 分段编辑 —— 让用户"驯化"自己的 AI ⭐⭐

**为什么做这个**：很多用户想微调 Prompt，但一整坨文本无从下手。

**我们的解法**：把 Prompt 拆成 4 段，每段独立可编辑：

```
┌─ 角色定义      → "你是高等数学助教..."
├─ 可用工具列表  → "你可以调 plot_function..."
├─ 注意事项      → "解题要先讲思路..."
└─ 其他补充      → 用户自由发挥
```

**实时预览**：你改任何一段，右边立刻显示合并后的完整 Prompt

**一键恢复默认**：改崩了点一下就回来

> 这个设计是真的解决了"想自定义又怕改坏"的矛盾。

### 亮点 5：纯前端离线可用 —— 0 部署 0 运维 ⭐⭐

**用户视角的 3 步上手**：
1. 双击 `index.html` 打开（或 `python -m http.server`）
2. 设置里填 API Key（默认预填 DeepSeek）
3. 开始问数学题

**工程实现**：
- 所有依赖（KaTeX、Plotly、math.js、marked、highlight）都丢在 `lib/` 目录本地加载
- 字体（Noto Sans SC、JetBrains Mono）也本地化
- **断网也能用**，除了发 API 请求那一下
- 不绑定模型 —— 任何兼容 OpenAI Function Calling 协议的 API 都行（DeepSeek、GPT-4o、通义千问、智谱 GLM-4 都测过）

### 亮点 6：设置加密导入导出 + 数学符号键盘 ⭐

**加密导出**（v1.1 新增）：
- 设置可以密码加密导出成 `.enc` 文件
- 换电脑时粘一段密文就能恢复，不用手动记 API Key
- 用 **PBKDF2-HMAC-SHA256 + AES-256-GCM** 加密
- **彩蛋**：我们写了**纯 JS 兜底实现**，因为某些内嵌浏览器 `crypto.subtle` 是 undefined —— 兜底代码与原生 WebCrypto 二进制完全兼容

**数学符号键盘**：
- 输入框旁边一个 `Σ π ∫` 按钮
- 点一下弹出软键盘，希腊字母、微积分符号、矩阵符号一键插入
- 解决"想敲个偏导符号 ∂ 找了半天"的问题

### 亮点 7：学习统计 + 收藏夹 —— 让学习有迹可循 ⭐

**学习统计**：
- Token 用量（输入/输出分别统计）
- 工具使用次数按数学分支分类
- 引导用户发现自己"线性代数用得少" → 主动补强

**收藏夹**：
- 右键消息 → 收藏
- 工具卡片也能收藏
- AI 自动命名收藏条目（也可以双击重命名）
- 侧边收藏面板快速回顾

## 四、技术难点 & 踩坑分享（2–3 分钟）

### 1. 多 Stream 实例状态竞争
**症状**：连续发两条消息，输入框状态错乱
**根因**：旧 stream 实例的 `end` 事件在 finally 里覆盖了新实例的 `isStreaming`
**解法**：代际守卫 + 活跃流计数双重保险

### 2. GCM 加密 `crypto.subtle` 不可用
**症状**：某些内嵌浏览器（WorkBuddy 桌面端）`crypto.subtle === undefined`
**解法**：手写 590 行纯 JS 兜底（PBKDF2 + AES-256-GCM），与原生输出**二进制完全兼容**

**坑过的细节**：
- `gfMul` 的位序一开始写反了
- `ghash` 长度块必须用 `setBigUint64` 写 64-bit 大端，**不能**用 `setUint32`
- 测试用 Node 原生 crypto 做对照，5/5 加密 + 5/5 解密 + 5/5 篡改检测全过

### 3. SSE 流式 + 工具调用的混合解析
**痛点**：LLM 边输文本边决定调工具，文本和 tool_calls 在同一个 SSE 流里
**解法**：`stream-parser.js` 独立模块，文本走 `onContentDelta` 回调，工具调用累积到最后一次性 `yield` 出去

### 4. Plotly/Canvas 焦点系统的设计
**痛点**：嵌入聊天流的图表会"抢"滚轮事件，导致页面卡顿
**解法**：未聚焦时 `pointer-events: none` 穿透，点击/悬停后激活交互
**全屏切换**：用 `ResizeObserver` 监听容器尺寸，Canvas 自动重绘

## 七、Q&A 预演

**Q1：为什么不加个后端？**
A：定位就是"零部署"。加后端意味着用户要租服务器，违背"双击 HTML 就能用"的核心理念。状态都在 localStorage，换浏览器数据就没了 —— 这是个**有意为之**的权衡。

**Q2：29 个工具不嫌多吗？**
A：这就是四段式架构的价值。加新工具只动 4 个文件，核心代码零侵入。看起来 29 个很多，但每个平均不到 100 行。

**Q3：纯 JS 写 AES-GCM 性能扛得住吗？**
A：PBKDF2 100k 迭代大概 1-2 秒，加解密本身毫秒级。设置导入导出不是高频操作，性能完全够用。

**Q4：Function Calling 协议对模型有要求吗？**
A：需要模型支持 OpenAI Function Calling 协议。DeepSeek、GPT-4o、Qwen、GLM-4 都支持。普通聊天模型不兼容。
